# Daisy：一个 AI-Native CRPG 叙事引擎的设计拆解

## 0. 写在前面：核心命题——"Prompt 即引擎"

Daisy 是一个可视化的 CRPG 分支叙事引擎。输入几个关键词，输出一棵完整的可玩叙事树——带结构、带正文、带选择分支、带技能检定、带多结局。两天，一个人，6 个 commit。

但本文不打算写成一份产品介绍。笔者更关心的是一个设计问题：**当 AI 从"辅助工具"变成"架构基础"时，"引擎"这个概念本身会发生什么变化？**

传统 CRPG 叙事工具链（Aurora Toolset、Creation Kit、ink/Twine）的核心是一个运行时引擎加上一套人工内容创作管线。引擎负责解析和执行，人负责创作和填充。而 Daisy 的不同在于：它的"引擎"是 799 行自然语言编写的叙事设计系统（`prompts.ts`），而不是一个渲染管线或脚本解释器。如果把 AI 从 Daisy 中抽掉，剩下的只是一个 React Flow 画布和一个空的 SQLite 数据库——**产品不是变差了，是不存在了。**

本文将从生成流程、Prompt 设计系统、编辑-游玩循环、架构四个维度拆解这些设计决策，并通过三个版本（V3/V4/V6）的对比测试数据验证它们的有效性。

## 1. 核心生成循环：从关键词到可玩叙事

### 1.1 生成流程对比：单步生成 vs 两步生成

Daisy 的核心生成流程经历了一次关键的架构变迁：从 V3 的单步生成到 V4/V6 的两步生成。这不是一次渐进式优化，而是一次根本性的范式切换。

**A. 单步生成（V3）：直觉上最自然，工程上最脆弱**

V3 的方案是一次 API 调用同时输出叙事结构（节点拓扑、边连接）和全部正文内容：

```
关键词 → [单次 API 调用] → 完整 JSON（结构 + 正文）→ 画布渲染
```

问题在于，当参数组合推向高端（long + detailed + bifurcating），单次输出的 JSON 体积会急剧膨胀。一个 42 节点、每节点 150 字的故事，仅正文就超过 6000 字，加上结构字段和 edge 定义，总 JSON 长度轻松突破模型的输出 token 上限。而 JSON 不同于自然语言——被截断哪怕一个字符，整个输出都无法解析。也就是说，**一次"差一点"的生成和一次完全失败的生成，在工程上是等价的。**

**B. 两步生成（V4/V6）：关注点分离**

V4 将生成拆成两步：

```
                  Step 1                          Step 2
关键词 → [骨架生成] → 结构 JSON ──→ [分批内容填充] → 完整故事
          (titles, edges,               (prose per node)
           value shifts only)
```

Step 1 只生成"骨架"——节点标题、类型、连接关系、价值转换标签，不包含任何正文。JSON 体积极小（通常 < 4000 tokens），几乎不可能被截断。Step 2 将完整骨架作为上下文传入，分批为节点填充叙事内容，每批的输出量可控。

这个架构决策背后的洞察是：在结构化 JSON 输出中，**结构完整性比内容质量脆弱得多**。一段正文写得不够好，可以单独重新生成那个节点；但如果 JSON 的结构被截断——一个 edge 的 target 丢了，一个节点的类型字段被切掉——整个图谱就废了，没有局部修复的空间。因此，两步生成的本质是将高风险操作（结构定义）与低风险操作（内容填充）解耦，**用最小的 token 预算保护最脆弱的部分**¹。

> ¹ 这个思路在分布式系统中其实很常见：先写 WAL（write-ahead log）保证事务结构完整，再异步填充数据。两步生成可以类比为先写"事务日志"（骨架），再"回放填充"（内容）。笔者没有刻意模仿这个模式，但回头看确实是同一种工程直觉。

### 1.2 参数空间与结构丰富度

Daisy 的生成参数构成一个多维配置空间。这些参数并非简单叠加，而是通过乘法关系互相影响：

| 参数维度 | 选项 | 影响范围 |
|---------|------|---------|
| **结构预设** | linear / bifurcating / funnel / web | 图谱拓扑形态、基础节点数、结局数 |
| **复杂度** | 1-5 | 幕数、分支密度 |
| **内容长度** | short / medium / long | 节点目标数乘数（0.6× / 1.0× / 1.5×） |
| **细节丰富度** | concise / standard / detailed / extreme | 每节点字数上限、节点密度因子、写作风格 |
| **诗意模式** | on / off | 关键词解读方式（隐喻 vs 字面）、温度（0.9 vs 0.7） |

以节点目标数为例，它的计算公式是：

```
nodeTarget = min( presetBase(complexity) × lengthMul × detailNodeFactor, 50 )
```

其中 `detailNodeFactor` 在 extreme 模式下为 1.8，在 detailed 模式下为 0.55。这个 3 倍以上的差距意味着 extreme 和 detailed 代表了两种截然相反的叙事哲学：**extreme 追求 McKee 所说的"beat 级粒度"——每个节点只承载一个动作-反应单元（40-80 字），节点之间的价值极性交替振荡（+/-/+/-）；而 detailed 追求场景级的沉浸感，每个节点包含完整的对话交换、环境描写和价值转换（最多 150 字）。** 换言之，同一个故事在 extreme 下可能有 40+ 个快速跳切的节点，在 detailed 下可能只有 18 个沉浸式场景。

以实际对比测试数据为例（关键词：深海空间站 · 失联信号 · 变异体，参数 long + detailed + bifurcating）：

| 版本 | 节点数 | 结局数 | 生成稳定性 |
|------|--------|--------|----------|
| V3 | 33² | 5 | 5 次中 2 次成功（**60% 失败率**） |
| V4 | 35 | 6 | 8/8 全部成功 |
| V6 | 42 | 8-9 | 8/8 全部成功 |

> ² V3 的数据来自成功的 2 次测试。失败的 3 次均为 JSON 截断导致解析错误，输出完全不可用。

从数据中可以得出两个结论：

**第一，两步生成彻底消除了截断风险。** V4/V6 在 16 次测试中保持 100% 成功率，而 V3 在相同参数下失败率高达 60%。这不是概率波动——在 long + detailed + bifurcating 这个参数组合下，V3 的单步输出几乎必然超出安全 token 范围。也就是说，V3 在这个参数空间里不是"偶尔失败"，而是"结构性不可用"。

**第二，Prompt 的叙事规则直接影响结构丰富度。** V6 相比 V4，在完全相同的参数下多生成约 20% 的节点和 33-50% 的结局。两个版本的生成架构完全一致（两步生成，相同温度，相同模型），唯一的变量是 V6 新增的反套路规则和游戏写作规则。这些规则封堵了模型的廉价叙事捷径——当"突然黑暗降临"和"一切都是幻觉"被禁止后，模型不得不构建更多独立的分支路径来达成叙事复杂度，**结果反而产生了更丰富的结构**³。

> ³ 这是一个有意思的发现：对生成式模型施加更严格的约束，输出不一定更保守——反而可能更丰富。类比围棋：规则越简洁，变化反而越多。当你封堵了"偷懒"的路径后，模型被迫在更大的解空间中探索。

## 2. Prompt 作为叙事设计系统

### 2.1 McKee 六条硬约束的编码

799 行的 `prompts.ts` 不是一个"帮我写个故事"的指令，而是一套用自然语言编写的叙事设计专家系统。其核心是 Robert McKee《Story》中提炼的六条硬约束——系统 Prompt 的措辞是"every scene you generate MUST satisfy ALL six"，不是建议，是强制：

| 约束 | McKee 原理 | Prompt 中的实现方式 |
|------|-----------|------------------|
| **Value Shift** | 每个场景必须转换至少一个价值 | 强制输出 `valueBefore` / `valueAfter` 字段 |
| **Progressive Complication** | 后续节拍递进加压 | "never plateau" |
| **Dilemma** | 选择必须是不可调和的困境 | "no obviously right choices" |
| **The Gap** | 行动与结果之间存在落差 | "the result is always different than expected" |
| **Controlling Idea** | 全篇一个统一主控思想 | 顶层 `controllingIdea` 字段贯穿所有幕 |
| **Three Levels of Conflict** | 内在/人际/超个人三层冲突 | 生成时要求 inner/personal/extra-personal conflict |

笔者在测试中观察到一个现象：**将抽象的叙事理论转化为结构化的输出字段，比用描述性语言提要求有效得多。** 以 Value Shift 为例，如果只在 Prompt 里写"每个场景都要有价值转换"，模型经常用一句"气氛变得紧张了"蒙混过关。但当你要求它在每个节点上显式输出 `valueBefore: "信任"` / `valueAfter: "怀疑"` 时，它就必须在生成内容之前先"想清楚"这个场景到底转换了什么价值——这相当于把 McKee 的理论从一个风格建议变成了一个可验证的结构约束⁴。

> ⁴ 当然，LLM 并不保证 100% 遵守指令。但结构化字段的违反是容易检测的（`valueBefore === valueAfter` 就说明没有转换），而描述性语言的违反几乎无法自动检测。也就是说，结构化约束不仅提高了遵守率，还降低了验证成本。

### 2.2 游戏写作规则与反套路机制

V6 新增了两组规则，分别解决两个不同层面的问题。笔者在 V3/V4 的大量测试中反复观察到这两个问题，它们的存在直接削弱了输出作为"可玩叙事"的有效性。

**A. 游戏写作规则——解决"体裁错位"**

模型的默认倾向是写"小说"而不是"游戏脚本"。具体表现为：大段环境描写先于事件发生、被动叙述（"一个阴暗的走廊出现在眼前"而非"你推开门，走廊尽头有什么在动"）、玩家作为旁观者而非参与者。这在传统文学中完全合理，但在互动叙事中是致命的——**玩家需要感到自己在"做事"，而不是在"读书"。**

在传统游戏引擎中，这个体裁约束是由引擎的交互机制自然产生的：你不得不把文本写成可触发的对话、可检查的物品描述、可响应的事件——引擎的 API 本身就在约束你的写作方式。而在 Daisy 中，AI 生成的是纯文本，没有引擎 API 来施加这种约束。因此，**体裁规范必须显式编码在 Prompt 里**，成为 V6 新增的七条游戏写作规则：

1. **Player as agent** — 主角主动行动，主动语态
2. **Show through interaction** — 不描述房间，让玩家通过交互发现
3. **Keep it punchy** — 最多 2-3 句描写，然后必须发生事件
4. **Concrete game information** — 输出可用物品、NPC、威胁、线索
5. **Dialogue is gameplay** — NPC 对话推进信息、制造困境
6. **Tension through stakes** — 通过事件制造张力（"氧气还剩三小时"），而非辞藻
7. **Active setup** — 世界观建置也是交互式的：探索、调查、对话

这些规则的本质是在 Prompt 层面定义了一种独立的文本体裁——"可交互的叙事游戏文本"。它既不是小说，也不是剧本，也不是 MUD 式的第二人称文字冒险⁵。

> ⁵ 这也是笔者认为"Prompt Engineering"这个词被严重低估的原因。799 行不是在"调参"——它是在用自然语言构建一个领域专家系统，把叙事设计师的方法论、游戏编剧的行业规范、JSON 序列化的工程约束压缩进一段文本里。传统游戏行业里，一个资深叙事设计师需要多年积累这些知识；现在，这些知识可以被编码、被版本管理、被 A/B 测试。

**B. 反套路机制——解决"模式坍缩"**

LLM 在叙事生成中有明显的模式偏好。当你用同一个模型生成数十个故事后，会发现"突然黑暗降临""一切都是幻觉""主角其实是 AI"等廉价反转的出现频率高得惊人。单独看某一个故事时，这些桥段可能有效；但当它成为模型的默认模式时，叙事就变得可预测——而可预测性恰恰是 McKee 所说的 Gap（预期落差）的反面。

V6 的反套路规则直接封堵这些模式：

- 禁止直接命名情绪（"他感到恐惧"），改用行动和对话展示
- 每个节点最多一个身体感觉描写
- 禁止华丽隐喻，要求朴素精确的语言
- **不是每个场景都是危机**——要求包含幽默、尴尬、日常质感

最后一条需要展开说。LLM 的默认倾向是把每个场景都推向高潮——每个节点都在"震惊""揭示""背叛"。这导致叙事节奏完全失控：**当所有场景都是高张力时，高张力就等于没有张力，因为玩家的情绪阈值会迅速饱和。** 反套路规则迫使模型在高张力节点之间插入低张力缓冲——日常对话、黑色幽默、尴尬的沉默——这就像音乐中的"动态范围"，钢琴段（p）的存在是为了让强音段（ff）有冲击力⁶。

> ⁶ 值得一提的是，这条规则在 Prompt 中的措辞是"not every scene is a crisis — include humor, awkwardness, mundane texture"。用自然语言定义"动态范围"这种本质上是结构性的叙事属性，是 Prompt Engineering 的一个有趣挑战：你不能说"30% 的节点应该是低张力的"，因为模型不会计数；你只能通过描述性语言引导模型形成一种分布上的直觉。

### 2.3 版本迭代：V3 → V4 → V6 的设计演进

三个版本的差异可以归结为两个独立的演进轴：工程稳定性和叙事质量。

| 演进维度 | V3（353 行） | V4（597 行） | V6（799 行） |
|---------|------------|------------|------------|
| **生成架构** | 单步（结构+正文一起） | 两步（骨架→内容填充） | 两步（骨架→内容填充） |
| **JSON 稳定性** | 60% 失败率 | 100% 成功 | 100% 成功 |
| **反套路规则** | 无 | 无 | 有（anti-melodrama） |
| **游戏写作规则** | 无 | 无 | 7 条 |
| **extreme 模式** | 无 | beats[] 在节点内 | beat 级独立节点 + sequences |
| **温度配置** | 0.7（普通）/ 0.9（诗意） | 同左 | 同左 |

**V3 → V4 解决的是"能不能用"的问题（工程稳定性）；V4 → V6 解决的是"用得好不好"的问题（叙事质量）。** 这两个轴是正交的：V4 的两步生成是一个纯粹的工程决策，与叙事理论无关；V6 的反套路和游戏写作规则是纯粹的叙事设计决策，与生成架构无关。

笔者保留了三个版本的独立可运行包（分别监听端口 3003/3002/3001），可以随时对同一组关键词跑三个版本的生成对比。本质上，这是在对叙事设计方法论做可重复的量化实验⁷——相同的输入、相同的参数、不同版本的 Prompt，输出在结构丰富度和文本质量上的差异可以被直接观察和度量。

> ⁷ 笔者认为这是 Prompt 作为"引擎"的一个被低估的优势：**方法论迭代的成本极低。** 在传统引擎中，要验证"延迟合流是否比即时合流产生更好的分支体验"，你需要修改引擎代码、重新构建工具链、让叙事设计师重新制作内容，周期可能是数周。在 Daisy 中，你只需要在 Prompt 里加一条规则（"after a choice, develop each branch for 3-5+ unique nodes before any merge"），重新跑一次生成，10 分钟出结果。

## 3. 编辑-游玩双循环

Daisy 的交互不是线性的"生成→完成"，而是两个相互嵌套的循环：编辑循环（修改叙事图谱）和游玩循环（在图谱中推进体验）。

### 3.1 涟漪分析：编辑传播与叙事一致性

在分支叙事中，修改一个上游节点可能导致数十个下游节点出现逻辑断裂。传统叙事工具的做法是把这个负担交给设计师——你改了什么，你自己去检查下游。结果是叙事设计师会倾向于"前期设计好就不再改动"，这与迭代式创作的理念是矛盾的。

Daisy 的涟漪分析（`buildContinuePrompt`）试图解决这个问题：

```
用户编辑节点 A → 系统分析 A 的下游 DAG → 提取受影响节点
      → AI 根据编辑内容和 controllingIdea 重写下游节点
      → 用户审核并接受/拒绝修改
```

**核心设计意图是降低"编辑恐惧"——让修改变成一个风险可控的操作，而不是一个需要人工检查整棵树的苦力活。** AI 不仅会修改下游节点的正文内容，还会根据 McKee 六条约束重新校验价值转换链——如果上游节点从"信任→背叛"改成了"信任→犹豫"，下游节点的价值弧线也会相应调整。

### 3.2 PlayMode：D&D 检定系统与叙事分叉

PlayMode 的角色创建采用 D&D 5e 的 27 点购买法（point-buy），分配六项属性（力量、敏捷、体质、智力、感知、魅力），每项最低 8 最高 18。沿叙事树推进时，遇到选择节点做出抉择，遇到检定节点投 D20 + 属性修正 vs DC。

```
角色创建（27 点购买）→ 叙事节点 → 选择节点（抉择）→ 检定节点（D20）→ 结局节点
                          ↑_______________________________________|
                                      循环推进
```

检定系统的设计遵循一个原则：**每次检定都是一个有意义的叙事分叉，而不只是一个通过/失败的数值判定。** check 节点同时包含 `successText` 和 `failText`——成功和失败各自走向不同的叙事路径，**"失败"同样是一条完整的叙事体验，而非惩罚**。这与传统 CRPG 中"失败=重试"的范式不同：在 Daisy 中，一个智力检定失败并不意味着你被挡在门外，而是意味着你走上了另一条同样完整但方向不同的路。

这种设计选择直接服务于 McKee 的"Gap"原则——玩家掷出骰子时的期待（"我应该能通过"）和实际结果（"失败了，但发现了另一条线索"）之间的落差，恰恰是互动叙事中最天然的戏剧张力来源⁸。

> ⁸ 这也解释了为什么 Daisy 选择 D20 而不是更简化的判定机制（如"成功率 70%"的概率判定）。D20 的物理隐喻——掷骰子——为玩家提供了一个清晰的"仪式感"，让 Gap 的产生有一个具象化的触发点。而概率判定只是一个静默的后台计算，玩家无法参与到这个"期待-落差"的过程中。

## 4. AI-Native 架构：不是功能模块，是架构基础

### 4.1 与传统引擎的结构性对比

过去一年，"AI-Native"这个词被大量使用，但多数场景下它的含义不过是"接了个 ChatGPT API"。接 API 不是 Native，就像用了数据库不意味着你做了一个数据驱动的产品。笔者认为，判断一个产品是否 AI-Native 的标准很简单：**把 AI 去掉后，产品是变差了，还是不存在了。** 如果只是变差（少了个"AI 助手"功能），那 AI 就只是一个功能模块；如果不存在了，那 AI 就是架构基础。

| 维度 | 传统叙事引擎 | Daisy |
|------|-----------|-------|
| **核心引擎** | 渲染管线 + 脚本解释器 | 799 行 Prompt（叙事设计规范） |
| **内容创作** | 人工编写每个节点 | AI 生成 + 人工编辑 |
| **结构约束** | 引擎 API 强制执行 | Prompt 中的自然语言规则 |
| **方法论迭代** | 修改代码/工具链（周→月） | 修改 Prompt 文本（分钟→小时） |
| **技术栈** | Unity / Unreal / 专用引擎 | React Flow + Zustand + Hono + SQLite |
| **团队规模** | 叙事设计师 + 程序员 + QA | 1 人（48 小时） |

**传统引擎的"引擎性"体现在渲染和运行时；Daisy 的"引擎性"体现在生成约束。** 799 行 Prompt 中编码的 McKee 叙事理论、六种节点类型规范、edge sourceHandle 连接规则、反套路约束——这些构成了 Daisy 真正的"引擎"。而 React Flow、Zustand、Hono、SQLite 只是"壳"——如果你把 Prompt 换成另一套叙事理论（比如用 Campbell 的"英雄之旅"替换 McKee），输出的故事结构会完全不同，但技术栈的代码一行都不用改。

因此，"引擎"这个概念正在被重新定义。**当 AI 可以理解叙事结构、生成符合设计规范的内容、维护分支逻辑的一致性时，"引擎"不再需要是一个渲染管线和物理系统的集合体。它可以是一套设计规范和约束系统——用自然语言编写，用 git 管理版本，用对比测试迭代。**

### 4.2 对从业者的意义

**对叙事设计师：** 这不是取代工具，而是放大工具。V3 到 V6 的每一次迭代，本质上都是人类设计师在教 AI 什么是好的叙事。"禁止廉价反转"这条规则不会凭空出现——它来自读过无数烂故事之后提炼出的判断力。设计师的经验和品味决定了 Prompt 的质量，Prompt 的质量决定了输出的质量。**链条的起点始终是人。** 但链条的放大倍率变了——一条好的规则不是改善一个故事，而是改善这个 Prompt 生成的所有故事。

**对程序员：** 48 小时，一个人，60 个源文件，10279 行代码，一个可以跑的互动叙事引擎。这不是因为个人能力特殊——是因为 AI 编程工具（Claude Code）让一个人可以同时扮演前端工程师、后端工程师、叙事设计师和 QA。工具链变了，能够独立完成的项目规模的量级变了。

**对决策者：** "两天一个人"这个数字值得注意。不是因为产品简单——64 节点的分支叙事、D20 检定系统、实时涟漪分析、氛围画布⁹——这些在传统开发模式下是一个小团队几个月的工作量。这个数字说明的不是"人可以被替代"，而是**瓶颈已经从人力转移到了想法**。当执行成本趋近于零时，决定产出质量的就只剩下品味和判断力了。

> ⁹ 氛围画布（Ambient Canvas）是 Daisy 的另一个核心特性：从故事文本中提取情绪关键词，映射成五色调色板，画布背景、节点边框、光效全部跟着故事氛围走。但这个特性更偏视觉设计而非系统设计，本文不展开讨论。
